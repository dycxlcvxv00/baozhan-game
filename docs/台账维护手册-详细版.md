### 2.1 数据结构（`xp.json` 的 `records[]`）

```json
{ "dt": "2026-10-13 14:46:31", "role": "陌尘", "level": 89,
  "map": "空洞城寨", "tier": "T15", "mobLv": 88, "mobQty": 0,
  "pot50": false, "pot20": false, "stones": 689,
  "prev": 2103973943, "cur": 2114440142, "note": "",
  "affixes": ["角色攻击和施法增加40%", "怪物受到伤害减少30%"] }
```

| 字段                | 含义           | 取值规则                                       |
| ----------------- | ------------ | ------------------------------------------ |
| `dt`              | 打完图的**实际时刻** | `YYYY-MM-DD HH:MM:SS`，如实记录，**绝不因 8 点规则改写** |
| `role` / `level`  | 角色名 / 等级     | 陌尘 / 89                                    |
| `map` / `tier`    | 地图名 / 阶级     | 读截图，`T1`–`T19`                             |
| `mobLv`           | 怪物等级         | 读截图，与角色等级不同                                |
| `mobQty`          | 怪物数量加成 %     | **面板值 + 词缀之和**；无加成写 `0`；不确定写 `null`（显示 —）  |
| `pot50` / `pot20` | 经验药水         | `true` = 生效（显示 ✓）                          |
| `stones`          | 本次晶石掉落       | **以用户消息里的数字为准**（见 4.3）                     |
| `prev`            | 上次经验值        | **必须等于上一条的 `cur`**（脚本自动保证）                 |
| `cur`             | 当前经验值        | 读截图                                        |
| `note`            | 备注           | 如 `'狂暴'`                                   |
| `affixes`         | 地图词缀数组       | 可省略；页面「词缀」列显示条数，**鼠标悬停**看全文                |
| `gained`          | 显式本图收益       | **仅升级跨级时必填**（见 2.3）                        |

### 2.2 计算规则

- 本图获得经验 = `cur − prev`（升级跨级条目例外）
- 获得占等级% = 获得经验 ÷ **该记录自身等级**的总经验（`ltOf(r)` 查 `LEVEL_TOTALS`）
- 等级累计进度% = `cur` ÷ 同上（与游戏 Exp 条一致）
- **升级总经验映射**（页面 `LEVEL_TOTALS` 与 `xp.py` 的 `LT_MAP` **必须同步**）：

| 等级 | 总经验           |
| -- | ------------- |
| 86 | 1,999,268,000 |
| 87 | 2,125,066,400 |
| 88 | 2,260,637,300 |
| 89 | 2,396,208,200 |

升级时两边各加一行，历史记录口径自动不变。

### 2.3 升级跨级条目（#47/#66/#125/#137/#255 等）

升级当图**经验条换坐标系**，`cur − prev` 会算出巨负数。这是**设计不是错误**，别去"修"。

- 录入加 `--level 89 --gained <本图获得> --force`
- **`--gained` = 补满旧级所需 + 结转新级的读数**
- 记录写入显式 `gained` 字段，渲染端与 Excel 优先取它
- `prev` 仍是上一条 `cur`（旧级读数），`cur` 为新级读数

### 2.4 8 点结算规则（双时间口径 —— 核心设计）

> **明细永远记实际时间，只在统计时才按 8 点归期。**

```js
function xpSettleDate(dt){
  // time < 08:00:00 → 归前一天；否则归当天
}
```

- 例：9-27 凌晨 01:40 打的图，`dt` 仍是 `2026-09-27 01:40:33`，统计归入 **2026-9-26** 结算日
- 结算期 = 当天 08:00 → 次日 08:00
- 与晶石台账的 `settleDateOf()` 是同一条规则，**两边必须一致**

### 3.3 时间口径

```js
// 写入：如实记录实际时刻
rec = { date: nowDate(), time: nowTime(), real: 1, ... }
// 统计：8 点归期
settleDateOf(r) = (r.time < '08:00:00') ? r.date - 1天 : r.date
```

### 3.4 `real` 字段必须全链路透传（2026-09-29 修过的真bug）

**现象**：上午 8 点后打开，「今日」面板显示已录入 2 条，但当天根本没录。

**根因**：`pushRec` 写入 `real: 1`，但 `loadLocal()` 和 `adopt()` 两个反序列化入口漏拷了这个字段。于是 `settleDateOf` 走「无 `real` → 沿用 `date`」分支，凌晨录入的记录被错误归到当天。

**修复**：`loadLocal`/`adopt` 补上 `real` + `settleDateOf` 消歧兜底 + `healRealMarks()` 一次性自愈 + `recStamp` 排序键改归期口径。

**教训**：给记录加字段时，**写入 + 两个反序列化入口 + 排序键**要一起改，漏一个就会出现「刷新后行为突变」的鬼故事。

### 3.4.5 档位快照 + 日级获取口径（2026-11-09 改造，核心口径）

#### ① 档位快照（解决「历史记录被错挂到新档位」）

**问题**：档位标签一直按账号**当前**财富值现算。账号一升档，整段历史记录都会被当成新档位 ——
分析「档位 vs 产出」时数据全是错的。

**做法**：录入那一刻把档位状态**快照进记录里**，随记录一起存、一起同步。

```js
// pushRec() 写入

        pct: WEALTH_TIERS[tier-1][1], level: ... }
```

- 无快照（旧记录）→ 回退账号当前档位，标一个「估」字，悬浮提示「估算」

#### ② 日级 telescoping（解决「日内多次记录虚增」）

**问题**：旧口径是**逐条** clamp（`diff < 0` 记 0）。同一天先高→后低→再高时，
中间的负增量被丢掉、后面的正增量被完整保留 → 总量虚增。
实测全站虚增 **275,601 晶石、31 个结算日**受影响。

**新口径**：clamp 只在**日级**做一次。

```js
// dayGainMap(c)
dayRaw  = Σ 当日 (本条剩余 − 上一条剩余 + 本条卖出 + 本条秘境消耗)
          // 等价于 (该日末条剩余 − 该日首条之前的余额) + Σ当日卖出 + Σ当日秘境消耗
dayGain = max(0, dayRaw)      // ← 唯一的 clamp
```

**三个函数共用同一数据源**，所以三处数字永远一致：
- `dayGainMap(c)` —— 日级归集，唯一数据源
- `gainedDeltas(c)` —— 卡片「累计获取晶石」= Σ 日级 gain（主号扣内部转入）
- `dayTotals(c, dayRecs)` —— 日结面板「当日获取晶石」= 该日 gain
- `transferPlan(c)` —— 主号内部转入扣减计划，也用日级口径（原来用逐条 clamp，会算错）

**明细表另有一条线**：`recDeltas(c)` / `detailDeltas(c)` 给的是**逐条真实增量**（不 clamp，可为负），
所以日内录多条时每一行都能显示自己那一笔的产出，而不是把整天都堆在最后一行。

#### ③ 明细表合计行：把差额摆出来

逐条之和 ≠ 日级之和 —— 差额 = 所有「净增为负的日子」的绝对值之和。
典型原因：当天卖出或秘境消耗没记全，导致那天余额掉得比记录的产出多。
这些天按 0 计入产出（不虚增），差额在**明细表底部合计行**显式标注，不是隐藏起来。

| 位置 | 口径 | 用途 |
| ---- | ---- | ---- |
| 卡片「累计获取晶石」 | Σ 日级 gain | 总览 |
| 日结面板「当日获取晶石」 | 该日 gain | 单日 |
| 明细表「本次获取晶石」 | 逐条真实增量 | 定位到具体哪一笔 |
| 明细表合计行 | 逐条之和 + 与日级口径的差额 | 对账 |

### 3.4.6 「转移晶石」显式口径 + 明细表列序 + 按钮分离（2026-11-10 改造）

这一节是**当前最新口径**，改这块之前先读完。

#### ① 「转移晶石」从隐式推断改为显式输入

**旧口径（隐式）**：转移只能靠「本次出售 > 0 且 本次收入 = 0」来表达。
问题：这俩数字有业务含义（卖出量、卖多少钱），硬借用会让「转出」和「卖钱」永远混在一起，
而且没法同时记录「既卖了一点、又转了一点」。

**新口径（显式）**：卡片上新增独立的「转移晶石」输入框，落库为独立字段 `transfer`。

| 字段 | 含义 | 谁看它 |
|---|---|---|
| `daySold` | **真卖钱**的晶石数 | 「已出售晶石」列、卡片累计已出售 |
| `dayValue` | 卖钱拿到的收入（元） | 「收入」列 |
| `transfer` | **转给其他号**的晶石数（不计收入） | 「转移晶石」列、对方号的转移收入 |
| `xferTo` | 转移**目标账号 id**（`''` = 没转） | 目标号的「转移收入」自动行 |

**统一拆分函数**（页面 `recParts(r, c)` / Python `rec_parts(r, is_main)`）：

```js
function recParts(r, c){
  const soldRaw = Number(r.daySold)  || 0;
  const valRaw  = Number(r.dayValue) || 0;
  const xferRaw = Number(r.transfer) || 0;
  /* 主号（陌尘）是接收方：晶石来自小号转入，不会「转出」给陌尘自己 */
  if(isMainChar(c)) return { sold:soldRaw, xfer:0, value:valRaw };
  /* 新口径记录（xf=1）：显式填了 transfer 就彻底分开卖与转 */
  if(r.xf === 1){
    if(xferRaw > 0) return { sold:soldRaw, xfer:xferRaw, value:valRaw };
    /* 仍沿用老习惯（卖出>0、收入=0 却没填转移）→ 依旧按转移算，
       免得用户改用新输入框之前填的记录全变成「卖了却没收入」 */
    if(valRaw === 0 && soldRaw > 0) return { sold:0, xfer:soldRaw, value:0 };
    return { sold:soldRaw, xfer:0, value:valRaw };
  }
  /* 旧数据兼容：无 xf 标记的记录，沿用「卖出>0、收入=0 = 转移」 */
  if(valRaw === 0 && soldRaw > 0) return { sold:0, xfer:soldRaw, value:0 };
  return { sold:soldRaw, xfer:0, value:valRaw };
}
```

**关键设计决策**：
- **主号例外（已改，2026-11-11）**：旧模型里陌尘只接收不转出，
  所以 `isMainChar(c)` 曾经**永远不套用转移判定**。
  新模型是「任意号 → 任意其他号」，主号也能转给小号，
  → 判定改成：**只要显式填了 `transfer`，主号/小号一视同仁**，全额转出。
  只有「没填 transfer」时，主号才跳过旧的隐式转移判定
  （主号历史上 `daySold>0` 是真卖钱，不能被当成转移）。
- **`xf:1` 标记**：新录入的记录带 `xf=1`，表示「已按新口径解析」。
  没填转移又沿用老习惯的，仍然按转移算 —— 保证用户改用新输入框之前填的记录数字不变。
- **转移量要加回 diff**：转出的晶石离开本号余额，若不加回就会被算成当天净减少（负获取）。
  `dayGainMap` / `recDeltas` 的 diff 公式里 `+ xfer` 那一项**不能删**。

**全链路透传**（同 3.4 的教训）：`loadLocal()` / 云端 `adopt()` / 导入备份三处反序列化映射
**都要**带上 `transfer` 和 `xf`，漏一处字段就丢。

**接收侧扣减（已泛化，2026-11-11）**：`transferInByAcct(acctId)` 按**账号**
汇总收到的转入量 —— 新旧两种口径都算进去，
`transferPlan(c)` / `acctDeduct(c, date)` 据此从**该账号**的「获取」里扣掉，
保证两边配平（晶石不能在两个号上各算一次产出）。
> 旧版本只对主号（陌尘）做这件事，小号之间互转会重复计产。现已对任意账号生效。

### 3.7 「异界产出」与「已获取」的区别（2026-11-10 新增，务必分清）

**这是本项目最重要的一条口径。**

| 指标 | 含义 | 能不能用来算档位产出 |
|---|---|---|
| **异界产出**（`dunGain`） | 录入时单独填的「打异界掉落的晶石」，**纯净口径** | ✅ 唯一可用 |
| 累计获取（含集市） | 用「剩余晶石的差额」倒推：`(日末余额 − 日初余额) + 卖出 + 秘境消耗 + 转移` | ❌ 不可用 |

**为什么不能用后者**
混合口径里的余额变化不只有异界掉落，还混着**集市买入、任务奖励、邮件补偿**等。
而且混得比想象中更严重 —— 「累计获取」这个口径本身是**坏的**（它把「秘境消耗」
加了回来，而余额快照根本没反映这笔扣减）。实测残差在 **−2.1 万 ~ +34.4 万**之间乱跳：

| 日期 | XP 纯异界 | Δ余额 | 秘境消耗 | (Δ+秘境) − 纯异界 |
|---|---|---|---|---|
| 2026-09-26 | 13,532 | +2,224 | 0 | −11,308 |
| 2026-10-04 | 14,154 | −7,383 | 90,000 | **+68,463** |
| 2026-10-19 | 4,498 | +3,353 | 345,000 | **+343,855** |
| 2026-10-12 | 16,549 | −34,980 | 30,000 | −21,529 |

结论：**历史数据的「累计获取」和「秘境消耗」对不上，不能用闭合法回溯重算**，
闭合法只适用于**新录入**的数据。

拿混合口径去算「升档能多产多少晶石」，会把集市收益算成异界产出，**结论直接失真**。

**字段约定**

| 字段 | 位置 | 含义 |
|---|---|---|
| `dunGain` | 记录级 | 异界产出数值；`null` = 该条没记（**新记录不再写**） |
| `dg` | 记录级 | `1` = 该条的 `dunGain` 有效；`0`/缺失 = 无效（**新记录不再写**） |

- `dg` 标记很关键：**「没记」≠「产出 0」**。
  旧记录（2026-11-10 之前）没有 `dg`，一律视为「异界产出未知」，
  卡片上显示「未记录」而不是「0」，避免把「没记」误读成「没产出」。
- 录入时填 `0` 也算有效录入（当天打了异界但没掉落），所以 `dunGain` 不按流水口径处理。
- 主号（陌尘）的「已获取」会扣除转入，这部分与异界产出无关，不受影响。
  （2026-11-11 起：**任意账号**都会扣除自己收到的转入，不再只限主号。）

**相关函数**（页面 `index-records.html`）

| 函数 | 作用 |
|---|---|
| `dungeonGainOf(r)` | 单条记录的异界产出；`dg≠1` 返回 `null` |
| `hasDungeonGain(c)` | 该角色是否有任何带异界产出的记录 |
| `dungeonGainByDay(c)` | 日级归集 `{结算日: 产出}`，与 `dayGainMap` 同源同口径 |
| `dungeonGainOfDay(c, date)` | 某结算日的异界产出 |
| `dayTotals().otherGain` | **其他来源残差** = 余额口径「已获取」− 异界产出（集市/任务/邮件等）；没记异界产出时不可信，置 0 |

**回填脚本**：`scripts/backfill_dungeon_gain.py`

- 经验台账 `xp.json` 每条打图记录的 `stones` 字段 = 该次打图掉落的晶石（436/441 条有值），
  是纯净的异界产出，可直接回填成 `dunGain`。

  把每日合计挂到该结算日的**最后一条**晶石台账记录上。

**档位分析脚本**：`scripts/tier_dungeon_output.py`

- 用**纯净异界产出口径**重算「档位 × 每日产出」，并给每档标注**证据强度**
  （强 = 样本天数≥5 / 中 = 2~4 天 / 弱 = 有档位但无异界产出数据）。
- 同时输出**异界地图阶级 → 单次产出**（分位数），以及**关键检验**：
  日产出到底由「打了几次图」还是「单次产出高低」决定。
- 当前结论（2026-11-10，陌尘 23 天打图记录）：
  - 自然日口径 `corr(打图次数, 日产出) = 0.97`，`corr(单次均值, 日产出) = -0.29`
  - → **日产出几乎完全由「当天打了几次图」决定**，与单次产出高低基本无关
  - → 想评估「升档值不值得」，**必须用单次产出做对比**，用日产出会被次数波动完全淹没
- 档位快照 2026-11-09 才上线，历史档位无法还原 —— 早期数据没有档位证据，
  表格会如实标「弱」/「—」，**不要据此编结论**。

### 3.8 闭合反推 + 来源分桶：不用手填异界产出（2026-11-11 确立，当前口径）

**背景**：代练只报得出「每天打完的剩余晶石」，报不出「异界产出」，
也不该让他区分「哪些是异界、哪些是集市」。

**2026-11-11 的两个决策**（用户拍板）：

1. **「打造消耗」取消**。打造装备、买东西这类消耗和异界产出没有关联性，
   它只是「玩家花掉的晶石」，混进来只会污染异界产出的归因。
   UI 框撤掉；**底层仍然读取历史值**（历史记录里若有 `craft`，仍按流出加回，方程才能闭合）。
2. **「集市收入」取消**。改成在录「剩余晶石」时点一下**「异界」按钮**：
   点亮 = 本次收入来自异界；不亮 = 来自市集或转入。
   金额不用报 —— 余额的净增残差由系统自动算（见下）。

> 「转移收入」从来不是手填项：转出号填了「转移晶石」并选目标号后，
> 目标号自动出现「转移收入」，自动进入方程（§3.9）。
> 「今日打图场次」已彻底撤下（§3.10）。

**余额方程**（同一账号、相邻两次盘点之间）：

```
期末余额 = 期初余额 + 本段净增（残差） − 秘境消耗 − 本次出售 − 转移转出 + 转移收入

反解 → 残差 = (期末余额 − 期初余额)
              + 秘境消耗 + 打造消耗（历史兼容） + 本次出售 + 转移转出
              − 转移收入
```

**残差整体归桶**（这是本节的核心）：残差不再拆成「异界 + 集市」两个手填渠道，
而是**整段按锚点记录的来源标记 `dsrc` 归到一个桶**：

| `dsrc` | 归到哪个桶 | 界面显示 |
|---|---|---|
| `'dun'` | **异界桶**（参与档位→产出分析） | 「累计异界产出」 |
| `'mkt'` | **市集/转入桶**（不是异界产出） | 「累计市集/转入」 |
| 缺失（历史 751 条） | 异界桶，但标 `legacy=true` | 数字后带「推」角标、标题写「历史推定」 |

**为什么历史记录归异界桶**：旧 UI 从来没让填过「集市收入 / 打造消耗」
（751 条历史记录里 `mkt`/`craft` 两个字段**一条都没有**），内部转入也只有 1 条 ——
也就是说当年的净增基本就是打异界掉的。标 `legacy` 是为了界面如实标注，不掩盖来源。

**盘点锚点规则**（谁能提供「可信余额快照」）

| `gl` | 含义 | 能否当锚点 |
|---|---|---|
| `1` | 这条的剩余晶石是**本次实测**的 | ✅ 能 |
| `0` | 明确**沿用**上一次的余额 | ❌ 不能（不是一次新盘点） |
| 缺失/`null` | 2026-11-11 之前的历史记录（当时每条都报余额） | 余额**相对上一条变了**才算（没变 = 沿用值） |

- `gl` 必须**三态保留**（`1` / `0` / `null`），反序列化时统一成 0 会让历史记录切不出区间。
- ⚠️ **只有 `xf=1`（页面自己写的记录）才认 `gl` 的语义**：
  手机/设备端把老记录统一补成 `gl:0` / `mkt:null` / `craft:null`，
  那是「把缺失字段填成默认值」的副作用，**不代表「这次沿用了旧余额」**。
  照字面把 `gl=0` 当「沿用」→ 全站 751 条老记录一个锚点都没有 → **产出直接归零**。
  判定代码见 `closureSegments` 里的 `glOf(r)`。
- **第一条记录默认不作锚点** —— 它代表「开始记账时手里有多少」，
  是后面所有区间的期初余额；把它当锚点会把初始存量算成产出。
  **例外**：账号填了「初始存量 `initLeft > 0`」且首条是实测（`gl=1`）→ 首条就是第一个盘点点，
  第一天的产出也算得出来。现有 26 个账号 `initLeft` 全是 0，所以对存量数据零影响。

**区间口径**

- 区间 = **(上一锚点, 本锚点]**；期初 = 上一锚点的余额快照
  （首区间 = 第一条记录的余额快照，或 `initLeft`）；期末 = 本锚点的余额快照。
- **区间内的流水全部加回**（秘境消耗 / 卖出 / 转出 / 历史 craft）——
  它们发生在两次快照之间，余额差里已经扣掉了。
- **第一条记录自己的流水算不算**：看它的余额是「实测」还是「沿用」——
  - `gl=1` / 历史记录 → 余额是那一刻拍的快照，流水发生在快照**之前**，已含在存量里 → **不算**；
  - `gl=0`（明确沿用）→ 余额是从上一段搬来的，流水发生在沿用余额**之后** → **要算**。

**可算性**（不满足一律不给假数）

1. 一个区间只覆盖**一个结算日**（跨天 → 产出没法拆到每一天）；
2. 相邻区间的结算日**连续**（断天 → 余额差跨了多天，方程不闭合）；
3. 最后一个锚点之后若还有记录 → 那段余额没封口 → 标为不可算。

**负残差：保留并标红，不 clamp 成 0**
负数意味着「这段余额净减少」—— 花掉的比记下来的多（打造/买东西这类没记的支出），
或者余额口径有出入。把它抹成 0 就等于假装那天没亏，统计口径会被污染。

**字段约定**

| 字段 | 位置 | 含义 |
|---|---|---|
| `dsrc` | 记录级 | `'dun'` = 本次收入来自异界；`'mkt'` = 来自市集或转入 |
| `gl` | 记录级 | `1` = 这条的剩余晶石是本次**实测**的；`0` = 沿用值；缺失 = 历史记录 |
| `xf` | 记录级 | `1` = **页面自己写的**新口径记录。⚠️ 只有 `xf=1` 的记录才认 `gl` 的语义 |
| `xferTo` | 记录级 | 转移目标账号 id；`''`/缺失 = 没转 |
| `craft` / `mkt` | 记录级 | **只读兼容**（UI 已撤下）；历史数据里实际一条都没有 |

> ⚠️ `dsrc` **不复用**老字段 `dg`：老 `dg` 的含义是「手填 dunGain 是否有效」，
> 语义不同，混用会让反序列化把新记录误读成手填值。

**相关函数**（页面 `index-records.html`）

| 函数 | 作用 |
|---|---|
| `srcMark(r)` | 读出这条记录的来源标记（`dun`/`mkt`/`''`） |
| `closureSegments(c)` | 盘点区间列表（每个区间含 `v / known / src / legacy / why`） |
| `closureMap(c)` | 按结算日归集的闭合结果 |
| `closureGainOf(r, c)` | 某条记录的闭合残差；不可算返回 `null` |
| `closureSrcOf(r, c)` | `{ src, legacy }` —— 这条记录所在的区间归哪个桶 |
| `closureWhyOf(r, c)` | 不可算的原因（给 UI 展示） |
| `dungeonGainEffective(r, c)` | **异界桶**取值：`{ v, src }`，`src` ∈ `closure`/`legacy`/`manual` |
| `marketGainEffective(r, c)` | **市集/转入桶**取值 |
| `xferEventsTo(acctId)` | 转给某账号的全部转移事件（按物理时刻升序） |

**来源优先级**（`dungeonGainEffective`）

```

```

- **闭合反推优先**：它是方程解出来的，且自动包含转移收入，是当前最准的口径。
- 历史手填值（`dg=1` 的老记录）作为**回落**，闭合算不出来时仍能显示。

### 3.9 转移模型：任意号 → 任意号 + 5% 手续费（2026-11-11 确立）

**模型**：晶石可以在**任意两个账号之间**转移，不分主号/小号。

- 小号 → 小号：允许
- 小号 → 主号：允许
- **主号 → 小号：允许**（旧模型不允许，已改）
- 号 → 自己：**禁止**（弹窗里不列自己）

**目标选择**：录入卡片上的「转移晶石」旁有一个「转给 ▾」按钮，
点开是**弹窗选择器**，列出**除自己以外**的所有账号（主号带紫点、小号带绿点）。
选定后按钮显示「转给 小号乙 ▾」，落库写入 `xferTo`。

**5% 手续费**：`XFER_FEE_RATE = 0.05`

```
A 转出 100  →  B 实收 95（手续费 5 被吃掉）
```

两侧各自按「**实际发生的**」记账：

| 侧 | 记账 |
|---|---|
| A（转出号） | 余额 −100；转移收入 0；闭合方程里是 **+100（流出）** |
| B（接收号） | 余额 +95；转移收入 **自动显示 95**；闭合方程里是 **−95（流入）** |

→ **A、B 两侧的闭合方程各自独立成立**，异界产出不会被手续费污染。

**新老口径分离（关键设计，别合并）**

历史记录（没有 `xferTo` 字段）产生于「手续费」概念之前 → **全额到账，不扣 5%**。

```js
function xferFeeApplies(r){ return !!(r && r.xferTo); }
```

→ `xferFeeApplies(r)` 只对**写了 `xferTo` 的新记录**返回 `true`。
历史数据如果被静默扣 5%，主号历史收入会凭空缩水一大截 —— 这是绝对不能接受的。

**任意号扣减（泛化）**

谁收到转入，谁的「累计获取」就要扣掉：

```js
function acctDeduct(c, date){ return transferPlan(c)[date]?.use || 0; }
```

旧版本只对主号生效，小号之间互转会**重复计产**。现已对任意账号生效。

**跨账号缓存失效（全局数据版本号）**

闭合反推与「累计获取扣减」现在**跨账号**依赖别号的转移记录：
B 号的账要算 A 号转过来的钱，A 号一改，B 号的缓存就全废。

→ 引入全局版本号 `_dataVer`，任何账号的记录一变就 `bumpDataVer()`，
所有缓存签名都带这个号，自动失效。

**已知局限（必须诚实说明）**

- 转移收入自动带出**依赖转出号已录入**。若 A 号当天还没录，B 号侧显示 0；
  A 补录后 B 自动带出（`refreshXferInRows()` 会即时刷新所有卡片的转移收入行）。
- 目标号是**手动选择**的，不会自动推断。选错号不会报错，但钱会记到错的号上。

### 3.11 「异界」来源标记按钮（dsrc，2026-11-11 新增）

**位置**：录入卡片「剩余晶石」这一行的**右侧**，一个小圆点 + 「异界」两字的按钮。

**行为**：

| 按钮状态 | 落库 `dsrc` | 含义 |
|---|---|---|
| 点亮（绿） | `'dun'` | **本次收入来自异界** → 这段的净增残差进「异界桶」 |
| 不亮（灰） | `'mkt'` | 本次收入来自**市集或转入** → 残差进「市集/转入」桶 |

- 这是**录入级**的标记：每录一次，点一次。
- 状态存在内存变量 `_dgPick` 里，**按卡片下标**索引；
  **每次「录入」成功后自动复位为灰色**（`resetDgPick`，2026-11-12 改）——
  它声明的是「本次」来源，不是这个号的长期开关。
  ⚠️ 旧版行为是「录完不自动关」，已废弃：旧逻辑会让第二次录入被误标 `dun`
  （想连记两笔市集时尤其危险）。下一次要记异界，请重新点亮。
- 按钮文字是中文，不点亮时按钮是暗的、旁边的提示写着「不点 = 来自市集或转入」。

**为什么用它替掉「集市收入 / 打造消耗」两个框**

1. 打造消耗与异界产出**没有关联性**（做装备、买东西的消耗不该算成异界产出）；
2. 集市收入**可以从余额净增里算出来**（残差），让代练去区分「哪些是异界、哪些是集市」
   既不现实也不准；
3. 让用户做一次**非数值判断**（「这次的收入来自哪」）比让他报一个准不了的数字更可靠。

**注意**：不点按钮 ≠ 这段没有产出，而是这段产出被归到「市集/转入」桶 ——
异界桶的合计会少掉它，但「累计市集/转入」会多出来，两边加起来还是总净增。

### 3.12 数据节点（node）：分段起点机制（2026-11-10 起）

**为什么要有节点**

节点之前的老数据（751 条）里，「异界产出」是手填或旧口径算的，来源混着集市与系统奖励，
拿它做「档位 → 每日产出」的分析会失真。新模式（`dsrc` 来源标记 + 闭合反推）从零开始
积累才是干净样本。但老数据不能丢 —— 完整归档，随时可查、可回滚。

**节点 = 数据分析的一个新起点。** 一次「备份 + 节点打包」生成一个节点。

| 概念 | 含义 |
|---|---|
| 节点号 | `node1`、`node2`…（`node.id` / `node.seq`），编号递增，永不复用 |
| 节点日 | `node.date`，基线记录归期的那天 |
| 归档目录 | 私有仓库 `archive/<节点日>-<节点号>/`（全量备份 + 节点元信息） |
| 基线记录 | 每个账号在节点起点保留的**一条**记录 = 最后一次实测剩余晶石 |

**基线记录长什么样（关键设计，别乱改）**

```json
{
  "date": "2026-11-10", "time": "12:00:00", "real": 1,
  "gemsLeft": 9172,          // = 节点前最后一次实测的剩余晶石
  "gl": 0,                    // 沿用，不是本次实测 → 不作盘点锚点
  "bl": 1,                    // 基线标记 → 明细表显示「基」角标
  "xf": 1, "dsrc": "",        // 新口径记录，但不是一次收入，无来源
  "chaosCost": 0, "transfer": 0, "daySold": 0,
  "wealth": 157, "tier": 7, "pct": 300, "level": 84
}
```

账号级：`initLeft` = 基线余额，`gemsLeft` = 基线余额，流水累加字段清零。

**为什么这么设计**

- `gl: 0` → 基线**不作盘点锚点**；节点后第一条实测记录（`gl:1`）才是锚点
- `initLeft` = 基线余额 → `dayGainMap` 首行 diff = 0 → **累计获取从 0 起算，不虚增**
- `closureSegments` 首区间起点 = `recs[0].gemsLeft` = 基线余额
  → 节点后第一次盘点就能算出**真实产出**（残差 = 新余额 − 基线余额）
- 基线余额为 0 的账号（13 个）：`initLeft=0` → `hasInit=false`，机制完全一致

**页面上的表现**

| 位置 | 表现 |
|---|---|
| 顶部栏 | 新增「节点」标签：`节点 1 · 2026-11-10`；鼠标悬停显示归档目录、区间、条数 |
| 明细表 | 基线记录行显示金色「基」角标（`bl===1`），title 说明「节点期初的存量基准，不是一次录入」 |
| 云端不一致 | 云端有节点而本机没有 → 云端胶囊变红「节点不一致」，并**阻止本机推送**（避免旧数据覆盖云端节点） |

**`node` 字段的透传（踩过的坑）**

`saveLocal()` / `loadLocal()` / `serialize()` / `adopt()` / 导入备份 / 导出备份 —— 
**六处都必须显式透传 `node`**，因为它们全是逐字段映射，漏一处节点信息就在那次链路里丢失。
页面用 `readNode(data)` 统一解析，`sameNode(a,b)` 比对（比 `id` + `at`）。

**怎么切节点 / 查历史**

| 想做什么 | 怎么做 |
|---|---|
| 本机切到新节点 | 点右上角「**仓库恢复**」（同源下载 Pages 上的 `data.json`，覆盖本机） |
| 清空本机重来 | 浏览器控制台 `localStorage.removeItem('gem-ledger-v2')` 后刷新 |
| 查节点前的历史 | 私有仓库 `baozhan-data` 的 `archive/<节点日>-<节点号>/data.json` |
| 查节点的基线清单 | 同目录 `node.json` 的 `baseline` 映射（每账号：余额 / 时间 / 原记录数 / 档位） |

**打包脚本**

```bash
cd baozhan-data
python3 scripts/pack_node.py --node-id node1 --seq 1 --date 2026-11-10 --dry-run  # 预览
python3 scripts/pack_node.py --node-id node1 --seq 1 --date 2026-11-10            # 执行
```

### 3.13 卡面三来源分区 + 市集/转移分开统计（2026-11-11 夜改造）

**背景问题**：旧卡面只有一个「市集/转入」混合桶，市集卖的和别的号转来的混在一起，
永远分不开。而转移是**站内搬砖**（别的号调拨过来的晶石），不是赚来的钱，
混进产出会虚增收益、误导「档位 → 每日产出」的分析。

**核心结论（已用测试证明）**：闭合反推的残差公式是

```
v = (期末余额 − 期初余额) + 流出 − 转入
```

**转入已经被扣掉了** → 所以 `dsrc='mkt'` 桶里天然**不含**转移收入，
市集收入与转移收入**天然不重叠**，不需要额外拆分逻辑。

**三个来源的口径**：

| 卡格 | 口径 | 用途 |
|---|---|---|
| 异界产出 | `dsrc='dun'` 段残差之和（纯净） | **做「财富值档位 → 每日产出」分析只能用这个** |
| 市集收入 | `dsrc='mkt'` 段残差之和（已扣转入） | 不计入产出，但也不该被丢掉 |
| 转移收入 | 别的号转进来的**实收额**（已扣 5% 手续费） | 只反映站内搬运，不算收入 |
| 累计转出晶石 | 本号转给别的号的**全额** | 与「转移收入」成对看 = 本号的净调拨量 |
| 转移净额 | 转移收入 − 累计转出 | 正数 = 净吸晶石，负数 = 净输出 |

**恒等式（测试已锁）**：`余额总增 = 异界产出 + 市集收入 + 转移实收`

**卡面布局**（`.srcrow` 横排三格，跨满整行）：

```
│ 累计已出售晶石  │ 人工费用          │   ← .stats 两列，各 4 项
```

### 3.15 负残差归因：打造消耗（2026-11-12）

**问题现象**：陌尘的卡面「市集收入」显示 **-14198**（负数），
「晶石净值」也跟着被污染（21982 − 14198 = 7784，看起来像只赚了 7784）。

**根因**：打造消耗的录入框早在 2026-11-11 就撤了（用户要求），
用户没法手填打造花了多少晶石。于是：

```
22:21  余额 36224  [异界]
22:25  余额 27336  [市集]   ← 余额少了 8888，但没记任何支出
22:34  余额 25426  [市集]   ← 又少了 1910
00:09  余额 40144  [市集]   ← 收到转入 18118，扣掉后还差 3400
```

闭合反推的残差 = `区间净增 + 已记流出 − 转入`，这三段算出来是负的
（−8888 / −1910 / −3400 = −14198）。**残差为负的含义是「有一笔支出没被记录」**，
不是「收入是负的」。旧逻辑把它原样塞进「市集收入」桶 → 市集收入出现负数。

**用户更正的规则**：
> 如果出现负值，且没有打秘境和转移，则这笔支出就是用于装备打造了。

**实现**：

1. `closureSegments()` 里把残差拆成两半：
   - `v` = 收入侧的非负部分（负数一律取 0）→ 进异界/市集桶
   - `unrec` = 未记录支出（正数）→ 单独走
   - `unrecKind` = 归因：
     - `'craft'` —— 该区间**无秘境消耗、无转出** → 判定为打造消耗
     - `'other'` —— 区间内混了秘境/转出 → 无法归因，单列「待核对支出」
2. `totals()` 新增三个字段：
   - `craftCost` —— 已记录的 craft 字段累计（历史数据）
   - `craftInferred` —— 由负残差推断的打造消耗
   - `unrecordedOther` —— 无法归因的待核对支出
   - `craftTotal` = `craftCost + craftInferred`（卡面「装备打造」格显示这个）
3. **市集/异界桶永远不再出现负数**，「晶石净值」不被污染。

**顺带修掉的另一个老缺陷**：`dayGainMap()` 的日级 clamp

```js
g.gain = g.raw > 0 ? g.raw : 0;   // ← 负的那天整段丢成 0
```

`raw` 混着「产出」和「未记录支出」。一段里既有异界产出（+200）又有打造消耗（−300）时，
`raw = −100` 被 clamp 成 0 → **产出的 200 也一起丢了**，
于是「累计获取」与闭合法口径差 14198（实测值）。

现在改为：

```js
const gross = g.raw + unrec;      // 把支出从净额里摘出去，剩下纯产出
g.gain = gross > 0 ? gross : 0;   // clamp 仍保留在毛产出上
```

clamp 的原意（防止漏记流水导致虚增）依然保留 —— 纯亏损日（无产出）仍然计 0，不是负数。

**修正后的口径关系**（两套独立实现交叉验证一致）：

| 口径 | 定义 | 与另一套的关系 |
|---|---|---|
| 闭合法毛产出 | `异界产出 + 市集收入` | === `gained()` ✓ |
| 日级毛产出 | `gained()`（累计获取） | === 闭合法毛产出 ✓ |
| 净赚 | 毛产出 − 装备打造(含推断) − 秘境消耗 | 两套算法结果一致 ✓ |

**恒等式**（测试已锁）：
```
Δ余额 = 毛产出 − 未记录支出 + 转入 − 已记流水
```
实测全站差 = 0。

**测试**：`tests/test_dungeon_gain.cjs`【12】【13】段共 25 项新断言
（负残差归因、反例：有秘境/有转出不归打造、正例：秘境加回后残差为正、
毛产出两口径交叉验证、纯亏损日 clamp 仍生效）；
`scripts/test_e2e_negres.py` 15 项 e2e 断言。

### 3.16 卡宽下限 340px：消除开关行标签折行（2026-11-12）

**问题现象**：用户反馈「标签跳行」。实测确认是**开关行折行** —— 开关行是
「财富值 + 档位 + 背包 + 市集 + 宠物 + 代练」6 个标签，其中「代练」用
`margin-left:auto` 靠右。卡宽不够时它会被挤到**第二行**，卡片高度参差。

**精确定位**（26 个真实账号，卡宽逐 4px 扫描）：

| 卡宽 | 折行卡片数 |
|---|---|
| ≤312px | 19 ~ 26 个（全折） |
| 316 ~ 328px | 1 ~ 4 个（陌尘「财富 1674」最宽，最后才撑破） |
| **≥332px** | **0** |

**对应到视口**：`auto-fill` + `1fr` 下，卡宽 = (内容区宽 − gap×(n−1)) / n。
下限 320px 时，**2048px 视口**会算出 6 列 × 323px —— 正好落在折行区间：

| 视口 | 改前 | 改后 |
|---|---|---|
| 1366 / 1600 / 1920 | 3×430 / 4×378 / 5×350 | **完全不变** |
| **2048** | 6×323 ← **2 个卡片折行** | **5×390** ✓ 折行消除，卡宽 +67px |
| 2304 / 2400 / 2560 | 6×348 / 6×348 / 7×348 | **完全不变** |
| 3000 / 3440 | 7×365 / 9×350 | **完全不变** |
| **3840** | 11×333（紧贴临界 332） | **10×368** ✓ 留出余量 |

**改法**：`#cards` 的网格下限 `minmax(320px,1fr)` → `minmax(340px,1fr)`。

**为什么选 340 而不是更大**：340 越过临界点 332px 并留 8px 余量，
而且**只在原本会折行的那些屏幕上才掉一列**（要加宽就必然少一列），
1920 / 2560 / 3440 等常用宽度的列数与卡宽**一点都不变**。

**测试**：`scripts/test_e2e_cardsrc.py` 新增 8 项断言 ——
在 340 / 360 / 400 / 440px 四档卡宽下，锁死「开关行不折行」+「无标签换行/溢出」。

**顺带修掉 e2e 的 flakiness**：页面 boot 时会 `fetch` 远端 `data.json` 并覆盖
`localStorage` 里的种子数据，导致断言结果随网络时序漂移（表现为「单独跑全过、
批量跑失败」）。已在 `test_e2e_cardsrc.py` / `test_e2e_negres.py` /
`test_e2e_ir_labels.py` 中拦截 `**/data.json*` 请求，本地 e2e 一律只用种子数据。
（`test_e2e_node.py` **不**拦截 —— 它测的就是云端节点状态，需要真实云端数据。）

### 3.17 计算体系正确性审计（2026-11-12）

用户要求「继续排查可能出现的问题，现在的计算方式是否已经正确」→ 对整个台账计算体系
做了一次**系统性审计**，覆盖闭合反推核心逻辑、转移双向记账、负残差归因、
三桶口径与总量恒等式，并验证页面显示值与内部计算值一致。

#### 3.17.1 审计结论：核心逻辑正确

用**真实云端数据**（26 账号）+ 归档数据（752 条历史）做量化验证：

| 检查项 | 方法 | 结果 |
|---|---|---|
| 区间方程恒等式 | 逐段验证 `end − start == raw + inflow − out` | **0 违例** |
| 异界桶守恒 | 闭合分段 vs `totals().dungeonGain` 逐号对比 | **0 不一致** |
| 市集桶守恒 | 同上 | **0 不一致** |
| 转移双向配对 | 每个转出都能在目标号找到对应事件 | **全部配对** |
| 手续费守恒 | 转出 19072 / 转入实收 18118 | 缺口 **954 = 5%** ✓ |
| 负残差不进收入桶 | 负残差 → `v=0`，归 `unrec` | 异界/市集桶**永不为负** ✓ |
| 负残差归因 | 无秘境无转出 → craft | 3 段**全在陌尘 11-10**，均无秘境无转出 ✓ |
| 全站总量 | `Σgained == Σ(异界+市集)` | **67538 == 67538** ✓ |

#### 3.17.2 修复的 3 个真实缺陷

**缺陷①：`recParts` 的「卖出忘填收入」误判成转移（双向污染）**

```js
// 改前（xf===1 分支）
if(valRaw === 0 && soldRaw > 0){ return { sold:0, xfer:soldRaw, value:0 }; }
```

新界面「本次出售」和「转移晶石」是**两个独立输入框**，用户完全可能
「卖了 1200 晶石但忘了填现金收入」（或本就是白嫖/送人）。
一旦误判成转移，后果是**双向污染**：

1. 本号：残差被加回 1200（凭空多出产出），「转移支出」格显示假值；
2. 陌尘：`xferTargetOf` 对无 `xferTo` 的记录默认返回主号 → 陌尘凭空收到
   1200 转入 → 闭合残差被扣掉 1200 → **真实产出被吃掉**。

构造测试实证（修复前）：

```
小乙 recParts = {"sold":0,"xfer":1200,"value":0}
陌尘 xferIn = 1200   ← 凭空多出来的转入收入
陌尘 异界桶 = 0      ← 真实产出应该是 0
```

**改法**：`xf===1` 分支删除该隐式判定（`xf!==1` 的老数据分支**必须保留** ——
归档里 39 条「卖出>0、收入=0」确实是当年的隐式转移）。
当前线上数据命中 **0 条**（修复是预防性的）。

**缺陷②：`unrecordedOutOf` 未检查 `known`（口径矛盾）**

不可算区间（跨结算日 / 断天 / 顺序错乱）的残差**不能**计入未记录支出。
该区间的 `v` 已因 `known=false` 被排除在收入桶之外，但 `unrec` 原来没同样排除
→ 出现「不可算」却仍显示「装备打造 +700」的矛盾（收入侧不算，支出侧却算了）。
`unrecordedByDate()` 早就检查了 `known`，这里补上同样的检查，两处口径才一致。

**缺陷③：档位分析脚本的口径污染与数据源缺失（最严重，直接卡住终态目标）**

### 3.18 财富值档位 → 每日异界产出映射（2026-11-12，用户澄清后重建）

#### 3.18.1 用户澄清与前提

用户明确模型假设：

> 「我再次给你明确，异界产出晶石数量，只和财富值有关」

这条推翻了 §3.17.5 的「缺件数和投入量字段」结论。**不应再加这两个录入项**，
而应直接从异界桶数据建立档位→产出的经验映射。

#### 3.18.2 方法学：为什么之前算错了

跨档位直接比产出，会被三件事污染：

| 污染源 | 表现 | 破解方法 |
|---|---|---|
| **当天投入环境** | 某天大家集体肝度 → 所有档位同时高 | 日固定效应 `gamma_day` |
| **日间随机波动** | 同一号今天 4000、明天 9000 | 每「号×档」取日产出**中位数** |
| **档位错标** | 凯西内尔 10 月还是 T3，历史记录却被标成当前档 T6 | 严格时点档位（见下） |

**严格时点档位规则**（`tier_upgrade_value.py` 的 `build_strict()`）：

- 带财富快照的记录 → 用它自己的档位；
- 无快照的历史记录 → **仅当**该号「最早快照档位 == 当前档位」才沿用当前档位；
- 否则（历史时期档位更低）整段丢弃。
  → 本次丢弃 **110 条**错标记录，保留 **434 条**日样本。

**模型标定**：以 T2（实测 4,669 晶石/天）为锚，

```
每日异界产出 = 4669 × (加成%_tier / 200) ^ b
```

`b` 用两种方法交叉验证：幂律回归 **1.687**、两两比值中位法 **1.709**，取 **b = 1.709**。

#### 3.18.3 结论一：产出是**超线性**的

```
log(每日异界产出) = const + 1.709 × log(加成%)     R² = 0.952   n = 17 个(号×档)
```

- **老结论「产出倍率 = 1 + 加成%/100」（T2 就是 ×3）已被实测推翻**；
- 实测：加成 200% → 218%（+9%），产出涨 **+15.9%**，不是 +9%；
- 但 `b` 的 95% 置信区间 **[0.84, 1.79]**，纯线性加成（b=1）**仍落在区间内**
  → 老规则不算全错，只是略微低估高段档位。

#### 3.18.4 结论二：用户的断言成立到什么程度

| 检验 | 结果 | 判定 |
|---|---|---|
| 同档不同号（T2，7 个号） | 日产出中位 4533~5039，号间 **CV = 0.034** | ✅ 高度一致 |
| 同日同档不同号（最严格，76 组） | 组内 CV 中位 **0.265**；24% 的组几乎相同，13% 差很多 | ⚠️ 大体一致 |
| 档位解释力 | 档位间 CV **0.915** vs 档位内日间 CV **0.493** | ✅ 档位效应是档位内波动的 **1.9 倍** |

> **准确表述**：财富值决定**产出基准**，投入量决定当天落在基准的**哪一档**。
> 档位是一阶决定因素，方向与量级都被数据支持；但不是唯一因素。

## 4. 标准录入 SOP

### 4.0 晶石台账录入（页面直接操作，index-records.html）

每天在卡片上填这些框（`剩余晶石` 是盘点值，其余是流水）。

**录入区布局（三行 + 剩余晶石独占一行）**：

```
┌─────────────────┬─────────────────┐
│ 出售晶石         │ 现金收入         │   第 1 行
├─────────────────┼─────────────────┤
│ 秘境消耗         │ 转移晶石         │   第 2 行
│                 │  [转给 ▾] 按钮   │
├─────────────────┴─────────────────┤
│ 剩余晶石（全行）  [● 异界] 按钮     │   第 3 行
└───────────────────────────────────┘
「转移收入」自动行（只读，从别的号自动带出）
```

| 输入框 | 填什么 | 口径 |
|---|---|---|
| `出售晶石` | 卖掉的晶石数 | 只算真正卖钱的；转给别的号填在 `转移晶石` |
| `现金收入` | 卖晶石收到的钱（现金） | |
| `秘境消耗` | 进秘境花掉的晶石 | |
| `转移晶石` | 转给别的号的晶石 | 填了就要点右边按钮**选目标号** |
| `剩余晶石` | 现在手上还剩多少 | 盘点值，填 0 也算有效录入 |
| `异界` 按钮 | **本次收入来自异界就点亮** | 不点亮 = 来自市集或转入 |
| `转移收入`（自动行） | 别的号转进来的晶石 | **不用填**，自动带出，已扣 5% 手续费 |

> 已删除：`异界产出`（自动反推）、`今日打图场次`（场次法撤下）、手填的 `转移收入`、
> **`打造消耗`**、**`集市收入`**（2026-11-11 改成「异界」按钮，理由见 §3.8 / §3.11）。

**推荐流程（代练只报「剩余晶石」也能算出异界产出）**

1. 代练报「剩余晶石」→ 填进 `剩余晶石`；
2. **这次的收入是打异界掉的，就点一下右边的「异界」按钮**（变绿）；
   若是市集/转入的收入，**保持不亮**；
3. 点「录入」→ 页面自动算出这段的净增残差，并按按钮状态归到
   「累计异界产出」或「累计市集/转入」。

原理见 §3.8。**不用再报任何数字**，也不存在「留空 vs 填 0」的坑。

**转移的操作顺序**

1. 填 `转移晶石`（比如 `100`）；
2. 点右边的 **「转给 ▾」** 按钮 → 弹窗列出除自己外的所有账号；
3. 选目标号 → 按钮变成「转给 小号乙 ▾」；
4. 保存 → **目标号的卡片立刻出现「转移收入 95」（已扣 5% 手续费）**。

注意事项：
- 弹窗**不会列出自己**，防止转给自己造成自循环。
- 目标号选错不会报错，但钱会记到错的号上 —— 存之前看一眼按钮上的名字。
- 手续费 5% 由**接收方承担**：转出 100，对方实收 95。
- 转出号当天还没录 → 目标号侧转移收入显示 0，**等转出号补录后自动带出**。

**自检**

- 卡片「累计异界产出」末尾带「（推算）」→ 说明是反推值，不是手填
- 明细表「异界产出」列：闭合反推的带一个「闭」角标，历史推定的带「推」角标
- **负数（标红）** → 这段余额净减少，多半是打造/买东西这类没记的支出，不是负产出
- 卡片「累计市集/转入」→ 标了「不点亮异界」的那些段落的净增
- 显示 `—` 的行：鼠标悬停会说明是「不可算」还是「没记录」
- 汇总区「内部转移（号↔号，已从累计获取中扣除）」行 → 确认扣除额和实际转账对得上

## 6. 常见坑与排错


| 现象 | 原因 / 处理 |
|---|---|
| 刷新后看不到新内容 | Pages/CDN 缓存，**Ctrl+F5** 强刷。或换 CDN 节点确认是否只是单节点滞后 |
| 页面显示「本地模式」 | 令牌未填或被清。点云端胶囊重新粘贴 |
| 页面显示「离线 · 用本地缓存」 | 云端拉取失败但本地有缓存。检查令牌权限与网络 |
| 令牌推送报 401 | token 过期或被 revoke，重新生成 |
| 令牌推送报 409 | `sha` 不匹配，多设备并发写。等一下重推（脚本已自动重试） |
| `raw.githubusercontent.com` 超时 | 沙箱内常见。改用 `api.github.com` 的 Contents API |
| `gh api` 报「please run gh auth login」 | **gh 未登录**，别用它查 Pages 状态；用 curl 抓页面比对 |
| `/root/baozhan-game` 创建即消失 | 沙箱限制，见第 7 节。用 `/workspace/baozhan-game` |
| `git push` 报 403 | 用了token。切回 SSH：`git remote set-url origin git@github.com:dycxlcvxv00/baozhan-game.git` |
| 当日卡片数字不对 | 检查 `dt` 是否落在 8 点前（归前一天）；**明细时间本身不要改** |
| 经验值对不上 | `prev` 必须严格等于上一条 `cur`；脚本自动保证，别手改 |
| `cur` 远小于 `prev`（#47/#66/#125/#137/#255） | **升级跨级，设计如此**，真实收益在 `gained` 字段。别去"修" |
| 名字不变绿（晶石台账） | 凌晨录入归前一天是**正确**的；8 点后录入仍不绿才需查 `settleDateOf` |
| 今天没录却显示已录入 | 见 3.4 —— `real` 字段在 `loadLocal`/`adopt` 漏拷 |
| 「已出售晶石」比历史少了一大截 | **不是 bug** —— 2026-11-10 起「已出售」只算真卖钱的，转给陌尘的量挪到了「转移晶石」列（见 3.4.6） |
| 明细表渲染出 `NaN` 字样 | 卡片模板里三元表达式的分支带了前导 `+`，被当成一元正号。`? '' :` 后面直接跟字符串，**不要在冒号分支前加 `+`** |
| 改了页面但线上没变 | Pages 仓库要单独提交（`baozhan-game`），`baozhan-data` 只放数据。见 10.1 |
| Python 镜像和页面数字对不上 | 跑 `compare_caliber.py`，它会逐角色逐日报出不一致项。**改口径后必跑** |
| Excel 与页面不一致 | 只能由 `xp.py excel` 生成，禁止手改 xlsx |
| 截图读不出 | 路径 `/root/uploads/wb-img-*/Clipboard_Screenshot.png`，用 Read 工具查看 |
| 多个用户编辑同一文件 | 不要另存副本，会互相覆盖 |
